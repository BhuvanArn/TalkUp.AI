# Internationalization (i18n)

The web app ships in **English** (`en`, source language and fallback) and
**French** (`fr`), with [i18next](https://www.i18next.com) and
[react-i18next](https://react.i18next.com). Frontend only: server emails and
the AI interview language are not covered.

Code: `web/src/i18n/` (`initI18n()` runs in `web/src/main.tsx` before the first
render). Translations: `web/src/locales/<language>/<namespace>.json`, bundled
with the app (no network loading).

## Language detection

1. The language saved by the switcher (`localStorage`, key `talkup.language`).
2. `navigator.languages`: the first entry whose primary subtag is `en` or `fr`
   wins (`fr-CA` gives `fr`, `en-GB` gives `en`, `de` is skipped).
3. `en`.

Only an explicit choice in the switcher is saved (`changeLanguage()` in
`web/src/i18n/index.ts`); the detected language is not, so a visitor who never
uses the switcher keeps following their browser. `<html lang>` always follows the
active language.

The switcher is `web/src/components/molecules/language-switcher`, placed next to
the theme toggle in the public nav (desktop and mobile menu) and in the app's
account menu.

## Namespaces

One JSON file per namespace and language. Each extraction PR writes **only to
its own namespace**.

| Namespace  | Content                                                                        | Written by     |
| ---------- | ------------------------------------------------------------------------------ | -------------- |
| `common`   | Shared words and the shared atoms/molecules (actions, status, generic errors, language names, switcher, modals, toasts…). Default namespace. | `app` PR only  |
| `landing`  | Public pages and their shell (nav, footer, 404).                               | `landing` PR   |
| `auth`     | Login, register, organization signup, email verification, password flows, form validation. | `auth` PR      |
| `app`      | Signed-in app: shell, applications, simulations, agenda, notes, diary, progression, chat, CV. | `app` PR       |
| `settings` | Profile, settings pages and organization admin.                                | `settings` PR  |

`common` is **frozen** for the other PRs: the `landing`, `auth` and `settings`
PRs may read existing `common` keys but never add, rename or remove one. If one
of them needs a shared word that is missing, it adds the key to its own
namespace. The `app` PR owns the shared atoms and molecules and extracts their
strings into `common`.

A new namespace needs a JSON file in **both** languages and an entry in
`NAMESPACES` (`web/src/i18n/config.ts`) and `resources`
(`web/src/i18n/resources.ts`).

## Keys

- Nested objects, **camelCase**. The first segment is the feature or
  component, one top-level object per feature: `sidebar.*`, `agenda.*`,
  `notes.*`, `loginForm.*`, `hero.*`. Then `element`, or `section.element`:
  `hero.title`, `pricing.candidates.cta`, `loginForm.errors.required`.
- Name keys by role, not by text: `hero.primaryCta`, not `hero.createAnAccount`.
- `en` is the source of truth. Add every key to `fr` in the same change: a unit
  test (`web/src/i18n/resources.spec.ts`) fails when a key exists in one
  language only or a value is empty.
- Keys are typed from the `en` files (`web/src/i18n/types.ts`): an unknown
  key or namespace fails `npm run tsc:check`.

## Using translations

```tsx
import { Trans, useTranslation } from 'react-i18next';

const Hero = () => {
  const { t } = useTranslation('landing');
  return <h1>{t('hero.title')}</h1>;
};
```

- **Other namespace** in the same component: list it,
  `useTranslation(['landing', 'common'])`, then `t('common:actions.save')`. The
  `t` of `useTranslation('landing')` alone does not type-check `common:` keys.
- **Outside React** (toasts fired from hooks, stores): `import i18next from
  'i18next'` and `i18next.t('auth:loginForm.errors.invalid')`, called at the
  moment the string is shown, never at module load (the language could change).
- **Interpolation**: `"greeting": "Hello {{name}}"` →
  `t('greeting', { name })`. Values are not HTML-escaped (React does it).
- **Plurals**: only `_one` and `_other`, in both languages; never add `_many`
  (or `_zero`, `_few`…). Pass `count`:
  `"sessions_one": "{{count}} session"`, `"sessions_other": "{{count}} sessions"`
  → `t('sessions', { count })`. `0` takes `_one` in French and `_other` in
  English. French counts in the millions would need `_many` and fall back to
  the English text: accepted, the UI never shows such counts.
- **Inline markup** (links, bold): `<Trans>` with named components, never split
  a sentence into several keys:

  ```tsx
  // "consent": "I accept the <terms>terms</terms>."
  <Trans
    ns="auth"
    i18nKey="register.consent"
    components={{ terms: <Link to="/privacy" /> }}
  />
  ```

- Translate `aria-label`, `alt`, `title` and `placeholder` too.
- Leave product and brand names (TalkUp, Umami), emails and URLs out of the
  JSON unless they sit inside a sentence.

### Module-level strings

Constants defined outside components (link lists, options, headlines) hold
**typed keys**, not text; `t()` runs at render time:

```tsx
import type { ParseKeys } from 'i18next';

export const SECTION_LINKS = [
  { hash: 'features', labelKey: 'nav.features' },
  { hash: 'pricing', labelKey: 'nav.pricing' },
] as const satisfies readonly { hash: string; labelKey: ParseKeys<'landing'> }[];

// in the component
const { t } = useTranslation('landing');
SECTION_LINKS.map((link) => <a key={link.hash}>{t(link.labelKey)}</a>);
```

`HERO_HEADLINES` follows the same pattern; the variant ids stay unchanged (see
[Landing hero A/B test](#landing-hero-ab-test)):

```tsx
const HERO_HEADLINES = {
  a: 'hero.headline.a',
  b: 'hero.headline.b',
} as const satisfies Record<HeroVariant, ParseKeys<'landing'>>;

<h1>{t(HERO_HEADLINES[variant])}</h1>;
```

**Validation (zod, `utils/validators.ts`)**: schema messages become i18n keys
and are translated where the error is displayed:

```tsx
type ValidationKey = ParseKeys<['auth', 'common']>; // 'validation.…' | 'auth:…' | 'common:…'

export const emailSchema = z
  .string()
  .min(1, 'auth:validation.emailRequired' satisfies ValidationKey)
  .email('auth:validation.emailInvalid' satisfies ValidationKey);

// in the form
const { t } = useTranslation(['auth', 'common']);
{error && <p role="alert">{t(error as ValidationKey)}</p>}
```

## Dates and numbers

Use the active language, never a hard-coded `'en-US'` / `'fr-FR'` or
`undefined` (browser locale):

```tsx
import { useLocale } from '@/hooks/i18n/useLocale';

const { dateFnsLocale, intlLocale } = useLocale();
format(date, 'd MMM yyyy', { locale: dateFnsLocale }); // date-fns
date.toLocaleDateString(intlLocale, { weekday: 'long' }); // Intl
new Intl.NumberFormat(intlLocale).format(total);
```

Outside React: `getLocale(getLanguage())` (`@/i18n/locale`, `@/i18n`).
Fixed machine formats (`yyyy-MM-dd`, `HH:mm` sent to the API or used in inputs)
stay as they are.

Not migrated yet (each area migrates its own call sites with its strings):
`application-card`, `interview-date-pill`, `next-event-card`,
`calendar-table` (+ `CalendarTableEventItem`), `roadmap-timeline`,
`chatbot/ChatWidget` (hard-coded `fr-FR`), `landing-page/account-counter`,
`routes/notes/{index,$noteId}`,
`hooks/calendar/{useCalendarTable,useMiniCalendar}`, `utils/calendarUtils`,
`utils/time`.

## Tests

- Vitest: `web/src/tests/setupTests.ts` pins `en` (`initI18n({ lng: 'en' })`), so
  existing text selectors keep matching English. Keep writing selectors against
  the English text. A test that switches language must switch back to `en` in
  `afterEach` (see `language-switcher/index.spec.tsx`).
- Components rendered in tests use the real translations: do not mock
  `react-i18next`.
- Playwright pins the browser locale to `en-US` (`web/playwright.config.ts`).

## Landing hero A/B test

The hero headline is translated, but the Umami variant ids (`a`, `b`, the
`HeroVariant` type, the `talkup.heroVariant` storage value and the `heroVariant`
event data) **must not change**: only the displayed text moves to
`landing.json`, under one key per variant (`hero.headline.a`,
`hero.headline.b`). See [ANALYTICS.md](ANALYTICS.md#hero-headline-ab-test).
